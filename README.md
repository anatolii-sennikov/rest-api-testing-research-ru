# rest-api-testing-research-ru

> [English version](README_EN.md)

Суть проекта — неофициальные переводы исследований по тестированию REST API и нейтральные резюме на русском языке.

Некоторое время назад для пет-проекта пришлось углубиться в теорию, исследования, современные практики и подходы. Конечно же, с обоснованием и подтверждением. Как и предполагалось, вся информация опубликована в оригинале — на английском языке.

Статей и информации собралось достаточно. С одной стороны — легальных публикаций в русскоязычном сегменте не обнаружил, с другой — есть люди, которым тема интересна, но читать оригинал тяжело. Так и было принято внезапное решение о создании такого репозитория.

Как оказалось, сделать нормальные переводы — это вопрос далеко не одного вечера (хотя я до сих пор не уверен, что они вышли нормальными). Это определённые правила и нормы, каноны. Пришлось выбирать между академическим переводом и неофициальным — условно сленговым, с достаточным вкраплением англицизмов.

## Кратко о работах

**Конкурс инструментов SBFT 2026: REST League.**

Организаторы сравнили пять инструментов и базовый RestTestGen на 11 реальных REST API по единой методике: час на сервис, десять прогонов, обнаружение дефектов, покрытие операций и кода. Лучший результат — у AutoRestTest; покрытие ветвей ни у одного инструмента не превысило 23%.

**AutoRestTest на конкурсе SBFT 2026.**

Победитель конкурса: инструмент сочетает граф зависимостей семантических свойств API, мультиагентное обучение с подкреплением и генерацию значений большой языковой моделью. На 11 API он нашёл в среднем 67,09 уникальных ошибок 5xx против 24,65 у второго места.

**WuppieFuzz: фаззинг REST API с учётом состояния.**

Фаззер с открытым кодом: по схеме OpenAPI строит цепочки запросов, мутирует их и направляет поиск по покрытию кода. Учитывает состояние API — проверяет не отдельные вызовы, а последовательности. На Petstore покрыл 17–20 эндпоинтов из 58; белый ящик быстрее выходит на плато, но итоговое покрытие не увеличивает.

**Покрытие тестами в микросервисных системах.**

Как измерить, какие эндпоинты микросервисов реально покрывают E2E- и API-тесты. Авторы предлагают метрики и автоматический расчёт по исходному коду и трейсам; на TrainTicket (41 микросервис, 262 эндпоинта) API-тесты покрыли 91,98% эндпоинтов, E2E — 45,42%, объединённое покрытие — 92,36%.

**Статический анализ, учитывающий микросервисы.**

Почему обычный статический анализ плохо работает для распределённых систем на разных языках и как его научить видеть межсервисные вызовы, зависимости и деградацию архитектуры. Прототипы находят компоненты с точностью и полнотой выше 95% и обнаруживают 11 видов микросервисных запахов кода.

**Открытые проблемы фаззинга REST API: сравнение инструментов.**

Семь фаззеров сравнили на 19 реальных REST API и одном искусственном API с внедрёнными дефектами, измерив фактическое покрытие строк. Лучшие результаты — у EvoMaster (56,8% в среднем) и Schemathesis (54,5%), но ни один фаззер чёрного ящика не превысил 60%. Анализ логов и исходного кода выявил шесть классов открытых проблем: аутентификацию, базы данных, внешние сервисы, несоответствия схемы, ограничения на строки и недостижимый код.

**Порождение фаззеров, учитывающих семантику.**

Можно ли превратить схему OpenAPI или GraphQL в фаззер, который проверяет не только формат, но и смысл ответов: коды ответов, заголовки, соответствие схеме, утечки информации. Schemathesis нашёл в 1,4–4,5 раза больше уникальных дефектов, чем лучший из остальных фаззеров, и был единственным, кто нашёл дефекты в четырёх сервисах.

**Автоматизированное тестирование REST API на основе спецификации.**

Можно ли тестировать REST API только по спецификации OpenAPI 3.x, без исходного кода. Метод генерирует и выполняет тест-кейсы в четырёх режимах — от полностью автоматического до участия пользователя; на наборе из 30 API получилось от 1 222 до 3 807 тест-кейсов.

## Этический минимум

1. **Смысл**. Не дописываем выводы, не сглаживаем слабости, не «улучшаем» утверждения автора. Верность ≠ дословность — но и не разрешение сказать за автора то, чего он не говорил.
2. **Всё, чего нет у автора**. Пояснение термина или контекста, комментарий к ошибке, оговорка, спор, своё выделение, — помечаем: скобки, сноска, «Прим. пер.». Читатель должен видеть, где автор, а где переводчик. При этом «нет в оригинале → в квадратные скобки» буквально не работает: получается текст, забитый квадратными скобками. Помечаем то, что добавляет смысл, а не каждую запятую.
3. **Ошибки**. Ошибка или подозрительное место в формуле, числе, коде, утверждении — либо оставляется как в оригинале, либо правится — но с пометкой, например сноской «в оригинале: …». «Как должно быть» — не догадка переводчика вместо голоса автора. Мелкую опечатку в прозе можно поправить без пометки. Контакт с автором помогает проверить ошибку или опечатку и уточнить термин. Это не требование лицензии и не обязательное условие — правило хорошего тона.
4. **Ответственность за перевод**. Ответственность за содержание перевода — на переводчике (в т. ч. при MT/LLM), не на модели и не на авторе оригинала. Если использовалось MT/LLM — в шапке строка «Подготовка перевода».
5. **Конфликт интересов**. Финансовые, рабочие, конкурентные или личные связи с авторами и их конкурентами, которые могут повлиять — или выглядят так, будто влияют, — на выбор статьи, формулировки и комментарии должны быть описаны в шапке или сопроводительном файле. Совпадение темы статьи с областью своих исследований — не конфликт.
6. **Уведомления автора**. Если лицензия разрешает перевод и публикацию — уведомление автора есть вежливость и правило хорошего тона.
7. **Права**. Три разных факта: лицензия/статус источника, основание, по которому вправе публиковать перевод, и лицензия самого перевода. Первые два в карточке, третий — в шапке перевода. Детали — в [ATTRIBUTION.md](ATTRIBUTION.md), текст лицензии — в [LICENSE.md](LICENSE.md). Перевод неофициальный: при расхождениях главнее оригинал.
